# AL HAMZA MERIDIAN — Trade Management System
### All 10 phases implemented as code

This is a real, runnable Next.js + Prisma project — not a mockup. It was written in a
sandboxed environment with **no internet access**, so `npm install` and a full build have
**not** been run against it. Do that first, in your own machine or in Claude Code, before
treating any of it as tested. Everything below was written carefully and cross-checked
for internal consistency (schema fields vs. code, permission codes, imports), but "I
checked it by reading it" is not the same as "it compiled and ran."

---

## What's actually built

**Phase 1 — Foundation:** company email + password login with mandatory 2FA (email or
SMS, per-user), 5 roles with database-stored permission defaults and per-user overrides,
login history, append-only activity log, 8-hour session auto-expiry, brute-force
lockout, your real logo and sampled brand colors.

**Phase 2 — Master data:** Buyers and Sellers (full field set from your spec, status
workflow, auto-generated BYR-00001 / SEL-00001 codes), Products with a reusable
structured quality-spec template builder.

**Phase 3 — Trade Confirmation:** the structured Quality Builder (repeatable
parameter/requirement/unit rows, not a text box), buyer/seller/product selection,
automatic AMT-TC-YYYY-00001 numbering that resets yearly, Save Draft vs. Generate
(issuing consumes a number and **automatically creates the linked Trade record** — kept
as a distinct entity per your correction), Download PDF, Duplicate, and an email-logging
flow.

**Phase 4 — Trade lifecycle:** the full status workflow from Draft through Trade
Completed plus Cancelled/On Hold/Disputed, seller contract & buyer PO fields (PO
optional), shipment + container tracking with manual status updates, document metadata
tracking per trade.

**Phase 5 — Finance:** payment recording (buyer/seller, advance/balance, received
tracking), brokerage terms per trade (USD/MT, percentage, or fixed — never hard-coded),
one-click **automatic brokerage invoice generation** with correct calculation per
structure type and AMT-BI-YYYY-00001 numbering, printable invoice.

**Phase 6 — Disputes:** full lifecycle (Open → ... → Settled/Rejected/Closed), claim
amount, buyer/seller responses, settlement tracking — raising a dispute also flags the
trade status as Disputed.

**Phase 7 — Reporting:** filterable trade report (buyer/seller/product/status) with CSV
export respecting the same margin-visibility permission as everywhere else.

**Phase 8 — Email:** all 9 template types from your spec, seeded and editable, with
placeholder tokens; every "send" is logged to a real Email History table attached to the
trade. **Actual delivery is not wired to a live provider** — see below.

**Cross-cutting:** global search across confirmation numbers, buyers, sellers, products,
contract/PO numbers, BL numbers, container numbers, invoice numbers, and dispute types —
an exact confirmation-number match jumps straight to the trade. The Commercial
Confidentiality layer (`view_margin` permission) strips seller/buyer price and margin
fields server-side everywhere a trade is rendered or exported, not just hidden in CSS.

**Phase 9 (testing) and Phase 10 (deployment) are on you** — I can't run a browser or a
live server from this sandbox. The checklist below is what to work through.

## Deliberately NOT built — and why

Per your own instruction not to claim an integration works before it's configured and
tested:

- **Real email/SMS sending.** OTP codes and "sent" emails currently log to the server
  console / database instead of delivering. Wire in SendGrid/SES and Twilio — see
  `src/lib/notify.ts`.
- **File storage for uploads.** Document and buyer/seller-document records store a
  `fileUrl` field, but nothing uploads bytes anywhere. Wire in Vercel Blob or S3, then
  point the "Add document" forms at a real upload endpoint.
- **Live shipping-line tracking.** Shipment status is manually updated by Operations.
  No carrier API is connected — you'd need to pick a specific shipping line's API (they
  vary a lot) and that's a real integration project on its own.
- **Server-generated PDF library.** Trade Confirmation / Contract / Brokerage Invoice
  "PDFs" are print-styled HTML pages using the browser's own Print → Save as PDF. This
  was a deliberate choice over an unverified PDF library (like `@react-pdf/renderer` or
  Puppeteer) given I couldn't test either here — it works immediately, in any browser,
  with zero extra dependencies. Swapping in a server-rendered PDF library is a reasonable
  upgrade later if pixel-perfect branded output becomes important.
- **Notifications.** The database table exists (`Notification` model) but nothing
  creates rows in it yet — there's no bell icon or automatic "payment overdue" /
  "shipment arriving" trigger logic. This needs its trigger points designed before it's
  worth building the UI.
- **Settings → brand colors aren't live-wired.** The Settings page stores color values,
  but the actual UI still reads from `tailwind.config.ts` (compiled at build time), not
  from that table. Changing colors there won't yet change the UI without also editing
  the Tailwind config and redeploying.

## 1. Run it locally

```bash
cd ahm-tms
cp .env.example .env
# Edit .env: set SESSION_SECRET to a random 32+ character string
# (generate one with: openssl rand -base64 32)

npm install
npx prisma migrate dev --name init
npm run prisma:seed      # roles, permissions, Owner login, email templates

npm run dev
```

Open http://localhost:3000, sign in with the Owner credentials the seed script prints
(default `owner@alhamzameridian.com` / `ChangeMe!12345` unless overridden in `.env`).
The OTP code prints to your terminal since no email/SMS provider is configured.

### A realistic first walkthrough once it's running

1. Products → add "Non-GMO Canola Seeds" with a few quality spec rows (Moisture, Oil,
   etc.) as a template.
2. Sellers → add Chester Commodities (or your own test seller).
3. Buyers → add Almahsoul Exim FZCO (or your own test buyer).
4. Trade Confirmations → New → build the confirmation using your sample trade data from
   the original brief, add quality spec rows, click **Generate Trade Confirmation**.
5. Open the resulting Trade record — walk it through the status workflow, add a
   shipment, add a container, record a payment, set brokerage terms, generate the
   brokerage invoice, try Download PDF on both the confirmation and the invoice.
6. Try the global search bar with the confirmation number.
7. Log in as a non-Owner role (create one via Users & Permissions) and confirm margin
   fields disappear from Trades, the Trade detail page, and CSV exports.

## 2. Going to production

Same path as before — Vercel (hosting) + Neon or Supabase (managed Postgres):

1. Push to a private GitHub repo.
2. Create a Postgres database on Neon/Supabase, copy the connection string.
3. In `prisma/schema.prisma`, change `provider = "sqlite"` to `provider = "postgresql"`.
4. Import the repo into Vercel.
5. Set env vars in Vercel: `DATABASE_URL`, `SESSION_SECRET`, `OWNER_EMAIL`,
   `OWNER_PASSWORD`. Leave `EMAIL_PROVIDER`/`SMS_PROVIDER` unset until wired for real.
6. Deploy.
7. From your machine, with `DATABASE_URL` pointed at production:
   ```bash
   npx prisma migrate deploy
   npm run prisma:seed
   ```
8. Point your domain at the Vercel deployment (Project Settings → Domains).

### Wiring real email & SMS
Implement the actual provider calls inside `sendEmailOtp()` / `sendSmsOtp()` in
`src/lib/notify.ts` (SendGrid/SES for email, Twilio for SMS) — currently both throw a
clear error if you set the provider env var without implementing the call, rather than
silently pretending to send.

### Wiring file storage
Pick Vercel Blob or S3, add an upload API route, and change the "Add document" /
buyer-seller document forms to upload there and store the resulting URL — currently
those forms just take a URL you paste in manually.
